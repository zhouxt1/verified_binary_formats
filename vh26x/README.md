# vh26x: verified H.264 and H.265 header parsers and encoders

vh26x decodes and encodes the headers of H.264 (ITU-T H.264, 06/2026) and
H.265 (ITU-T H.265, 01/2026) bitstreams, with proofs in Verus that the
decoder and the encoder are inverse to each other and to the standards'
syntax. It covers NAL unit headers, parameter sets, SEI framing, access
unit delimiters, filler data and slice headers, from the Annex B byte
stream down to each syntax element. It is built on `vbits`, the bit layer
the repository's other codecs share.

These headers are where video decoders parse untrusted input before
anything else. They are dense with Exp-Golomb codes, conditional syntax,
arrays sized by earlier fields, and cross-references between parameter
sets, and they are a recurring source of CVEs in FFmpeg, libde265,
GStreamer and the media stacks of phones and browsers.

## How it works

The syntax tables of H.264 §7.3 / Annex E and H.265 §7.3 / Annex E are
transcribed, structure by structure, into a small table language
(`vh26x-tool/syn/h264.syn`, `h265.syn`), line for line. From H.265
7.3.7:

```
st_ref_pic_set(stRpsIdx) {
    inter_ref_pic_set_prediction_flag = 0
    if (stRpsIdx != 0)
        inter_ref_pic_set_prediction_flag               u(1)
    if (inter_ref_pic_set_prediction_flag) {
        delta_idx_minus1 = 0
        if (stRpsIdx == num_short_term_ref_pic_sets)
            delta_idx_minus1                            ue(v) range(0, stRpsIdx - 1)
        RefRpsIdx = stRpsIdx - (delta_idx_minus1 + 1)   # (7-59)
        delta_rps_sign                                  u(1)
        abs_delta_rps_minus1                            ue(v) range(0, 32767)
        deltaRps = (1 - 2 * delta_rps_sign) * (abs_delta_rps_minus1 + 1)   # (7-60)
        ...
```

Each element carries the constraints its semantics give, with their
clause: `range`/`eq` (and `assert`) must hold, and `confeq`/`conf` are
the "shall" a decoder must not reject on. Inferences ("when not present,
inferred to be ...") and derived variables (the equations 7-n) are
assignments, so the environment is complete in both directions.

`vsync` compiles each table into a program: blocks of statements over
a pool of expressions. The programs are data (`vh26x-tool/src/gen/`,
regenerated by `vh26x-tool/regen.sh`). One interpreter, written and proved
once, decodes and encodes any program. `vh26x` is that interpreter and the
layers below and above it; `vh26x-tool/src/stream.rs` keeps the parameter
sets and gives each unit its context.

## The theorem

The **value** of a NAL unit is its *trace*: the values of its syntax
elements in the order its table reads them, plus the iteration count of
each `more_rbsp_data( )` loop. The **context** is what the table reads from
outside: the NAL unit header and the active parameter sets. For every
program `p` (that is, for any table, not only the two transcribed) and
every context `c`, in `rt.rs`:

1. **Round trip** (`theorem_enc_dec`). If the encoder accepts a trace `t`,
   writing bits `b`, the decoder reads `b` back as `t`, with the same
   environment.
2. **Non-malleability** (`theorem_dec_enc`). If the decoder accepts bits
   `b` as a trace `t`, the encoder writes exactly `b` from `t`. So each
   value has exactly one encoding, and two different streams never decode
   to the same syntax.
3. **Sound output.** The decoder accepts only traces the encoder accepts,
   by 2, and the encoder accepts only traces that satisfy every
   constraint in the table. So a decoded unit satisfies every `range`,
   `eq` and `assert` of its table, in its context. A `conf` that fails
   does not reject the unit; it only clears the result's conformance flag.
4. **Bounds.** Every value, syntax element or derived variable, lies
   within ±2^48. An operation outside its domain fails in both directions
   alike (a division by zero, a `%` of a negative, an index outside its
   array, a value past the bound, a loop past 2^24 iterations). So
   failures never break 1 and 2, and the executable code cannot overflow
   or panic.

For the slice headers, which are followed by slice data the tables do not
parse, the same holds for prefixes (`theorem_pre_enc_dec`,
`theorem_pre_dec_enc`). The decoder stops exactly where the header's
encoding ends, whatever follows.

The executable decoder (`xdec.rs`) is proved to compute the spec decoder
(`sem.rs`) exactly: the same trace and environment, or failure when the
spec fails. The executable encoder (`xenc.rs`) is proved to compute the
spec encoder whenever it succeeds.

The layers under the tables are proved the same way:

| Layer | File | What is proved |
| --- | --- | --- |
| Descriptors | `eg.rs` | `u(n)` (n ≤ 48), `ue(v)` (at most 31 leading zeros), `se(v)` and the SEI 0xFF-byte coding are prefix codes: each value has one code, and each code reads back as its value |
| RBSP | `rbsp.rs` | An RBSP is its SODB followed by `rbsp_trailing_bits( )`, in exactly one way (`theorem_rbsp_inv`, `theorem_rbsp_rt`). A slice's RBSP past its header holds slice data and `rbsp_slice_(segment_)trailing_bits( )` (`slice_tail_ok_x`) |
| Emulation prevention | `esc.rs` | `unesc` is the loop of H.264 7.3.1 / H.265 7.3.1.1 that drops `emulation_prevention_three_byte`, and `esc` inserts them. `unesc(esc(r)) = r` for every RBSP. For every NAL unit that satisfies the constraints of H.264 7.4.1 / H.265 7.4.2 (`nal_ok`), `esc(unesc(n)) = n`: escaping is unique |
| NAL unit | `nal.rs` | The composition: a NAL unit's bytes, its RBSP and its trace determine each other |
| Annex B | `annexb.rs` | `split` finds the NAL units of a byte stream. It is complete (NAL units with any zero bytes around their start codes split back into themselves) and sound (whatever it returns is such a padding of the stream). So a stream's NAL units are unique; an encoder's only freedom is the zero bytes |

Verification: `cargo verus verify -p vh26x` checks 194 obligations with 0
errors, in seconds.

## What is trusted

* **The tables.** Whether `h264.syn` and `h265.syn` say what the standards
  say is where the standard stays the judge. The proofs cannot check it;
  testing does (below and `difftest/h26x/`). The compiler `vsync` and the
  conversion from its output (`raw.rs`) are unverified for the same
  reason. The theorems hold for every program, so a bug there can give a
  table the wrong meaning, but cannot break the round trip or
  non-malleability.
* **The stream layer** (`vh26x-tool/src/stream.rs`). It dispatches on
  `nal_unit_type`, stores SPSs and PPSs, gives each unit its context, and
  activates a PPS when a slice refers to it. It decodes the PPS at that
  point, against the SPS then present (a PPS needs its SPS only when
  activated, H.264 7.4.1.2.1, H.265 7.4.2.4.2).
* Verus, Z3 and the Rust compiler.

## Scope

**H.264.** NAL unit header; SPS, including VUI and HRD, with the
scaling-list fall-back rules A and B and their default tables; SPS
extension; subset SPS, whose SVC/MVC/3D extension is kept as bits; PPS,
including the FRExt part; SEI framing (each message's type, size and
payload bytes); AUD; filler data; end of sequence/stream; slice headers,
including `dec_ref_pic_marking( )`, `pred_weight_table( )`,
`ref_pic_list_modification( )`, data partitions A/B/C and auxiliary coded
pictures. That is every profile of Annex A: all but the SVC, MVC and 3D
ones of Annexes G to J.

**H.265.** NAL unit header; VPS, including `vps_timing_info` and its
`hrd_parameters( )`, with `vps_extension( )` kept as bits; SPS, including VUI,
HRD, `scaling_list_data( )` with prediction and defaults, `st_ref_pic_set( )`
with the derivations of 7-61 and 7-62, and the range, SCC, multilayer and 3D
extensions; PPS, including the range and SCC extensions, with the
multilayer and 3D extensions kept as bits; SEI framing; AUD; filler data;
end of sequence/bitstream; slice segment headers, including
`pred_weight_table( )`, `ref_pic_lists_modification( )`, entry points and
the SCC fields. The profiles are v1, RExt and SCC.

**Kept as bytes** (verdict `raw`, still checked against 7.4.1 / 7.4.2):
H.264 NAL unit types 14, 20 and 21 (SVC, MVC and 3D slices and
prefixes) and reserved or unspecified types; H.265 units with
`nuh_layer_id` > 0 (the multilayer extensions, Annex F onward) and
reserved or unspecified types. SEI payloads are framed but not
interpreted. Slice data is not parsed.

**Decoders shall ignore.** Reserved values the standard says decoders
shall ignore are decoded and kept (`reserved_zero_2bits`, the
`*_reserved_zero_*bits`, `*_extension_4bits` with their data flags), and
they clear the conformance flag instead of rejecting.

## Results

`cargo test -p vh26x-tool` needs nothing but Rust: it checks 256 streams,
from vh26x-gen and mutants of them, on
which FFmpeg, GStreamer and libde265 agree with vh26x (the verdict and
values of each unit), and that every decoded unit re-encodes to its bytes.

The details:

* ITU-T conformance streams: 528 H.264 and 317 H.265. Every H.264 stream
  decodes (97,126 units, the rest kept raw). Every H.265 stream decodes
  (66,448 units), except SHVC's `ADAPTRES_A_ERICSSON_1`, whose VPS and SPS
  break 7.4.3.1 and 7.4.3.2.1. Every decoded unit re-encodes to its
  original bytes.
* FFmpeg, element by element: all 845 streams agree on every syntax
  element of every unit both decode (149,924 units).
* Structure-aware fuzzing (streams vh26x-gen draws from the tables and
  encodes) and mutation fuzzing against FFmpeg, GStreamer and libde265,
  including ASan/UBSan builds. Every disagreement is classified by a rule,
  as a departure of the reference from the standard or a gap in vh26x's
  tables (fixed, citing the clause). The harness and the departures it
  found will be published once they are reported upstream.

## Build and run

```bash
cargo build --release -p vh26x-tool
target/release/vh26x-tool --h265 --check stream.265     # verdict per NAL unit, re-encoded and compared
target/release/vh26x-tool --dump stream.264             # every syntax element, with its bit position
target/release/vh26x-gen --h265 7 out.265               # a random valid stream, from the tables

export PATH=$PWD/tools/verus-x86-linux:$PATH            # tools/get-verus.sh fetches it
cargo verus verify -p vh26x

vh26x-tool/regen.sh                                     # after editing a .syn file
```
